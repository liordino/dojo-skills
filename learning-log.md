# Learning Log — dojo-skills

Wave briefs and debriefs. Append-only.

## Wave 1 — Opening Brief

- **What:** add a new lint rule (R10) to `scripts/dojo-lint.sh` asserting that the dojo-check proof-contract identifiers (`check-proof`, `output_sha256`, `check-output.log`) appear in five surfaces: `dojo-principles/SKILL.md`, `scripts/dojo-check.sh`, `hajime/SKILL.md`, `DOJO-MANUAL.md`, and `hajime/reference/dojo-check.ps1`. The current R6 (byte-equality between hajime's block and the manual's block) stays in place during RED; GREEN retires it as R10 is filled.
- **Why:** ADR 0001 splits the source of truth — the proof-contract invariant belongs in `dojo-principles`, the stack commands belong in `scripts/dojo-check.sh`, hajime's inline block becomes illustrative. The new R enforces the *structural* agreement (every surface references the same identifiers), not the old byte-equality. Today `dojo-principles/SKILL.md` is silent on the proof contract, which is the gap the wave closes.
- **Concepts to explore:** *source-of-truth split* (one meaning, multiple normative layers), *structural vs byte-equality lint* (what the linter is allowed to assert), *ADR traceability* (the wave implements the ADR; the lint is the test that the ADR landed).
- **Bigger picture:** Wave 1 of 10. Wave 2 sets the invocation rule; Wave 3 ships the router; Wave 4 introduces the `_enforce_` and `_proof_` leading words. This wave's contribution is the *first* leading-word migration target: `_proof_`. Without it, the leading-word collapse in Wave 4 has no anchor file.

## Wave 2 — Opening Brief

- **What:** add a new lint rule (R11) to `scripts/dojo-lint.sh` that classifies every SKILL.md into one of three buckets per ADR 0002 (model-invoked, user-invoked, session-invoked) and asserts the YAML front-matter matches the category's contract. Model-invoked skills must *lack* `disable-model-invocation: true`; user-invoked skills must *carry* it; session-invoked skills must carry a `# invocation: session-invoked — see ADR 0002` rationale comment. Each skill belongs to exactly one category; double-classification and un-classified skills are both errors.
- **Why:** ADR 0002 establishes the rule; today zero skills carry the flag and zero carry rationale comments, so the rule is aspirational rather than enforced. R11 makes it *enforceable* — a single lint run verifies the rule is applied. After GREEN, the flag flip removes ~480 words of always-on context tax (per the audit), the three `dojo-*` files carry session-invoked rationale, and any future skill added without an invocation decision fails the gate at PR time.
- **Concepts to explore:** *enforce-over-instruct applied to skill design* (the rule lives in the ADR, the enforcement lives in lint, the audit lives in the route table), *three-bucket classification* (a category per skill, never overlaps, never missing), *rationale comments vs absent flags* (session-invoked skills look identical to model-invoked in the YAML parser; the comment is what distinguishes them to humans reading the front-matter).
- **Bigger picture:** Wave 2 of 10. After GREEN, the router skill (Wave 3) can land with a category-aware table of skills. Wave 4's leading-word collapse for `_enforce_` and `_proof_` benefits from the smaller context load. Future waves' skill additions automatically get an invocation decision at randori/kaizen time because the lint gate enforces it.

## Wave 1 — Closing Debrief

- **What was done:** added `## Enforce Over Instruct — the Proof Contract` to `dojo-principles` (the new normative home); reframed hajime's H3 + inline prose to "illustrative" with a pointer at the principle; mirrored the same in `DOJO-MANUAL.md` and moved the "former R6" provenance into a pointer at ADR 0001; retired `scripts/dojo-lint.sh` R6 (byte-equality between hajime's bash block and the manual's) and added R10 (structural-equivalence via identifier presence).
- **Why the approach works:** the lint now asserts what the wave's goal actually claims — *every surface agrees on the proof-contract identifiers* — instead of policing byte-equality between two surfaces that have no business being byte-equal. R10 failed for the right reason in RED (`dojo-principles/SKILL.md` was silent on the contract) and passed cleanly in GREEN once the principle file carried the rule. Trade-off accepted: surfaces are now allowed to diverge in prose, which means future maintainers can rephrase hajime and the manual independently so long as both still reference the three identifiers.
- **Systemic improvement opportunities:** none from this wave that didn't land — every observation from GREEN's refactor assessment either shipped (manual provenance cleanup) or turned out to be a non-issue on re-examination (R10 surface variables are already at the top of the rule; H3 redundancy was actually complementary; the proof-artifact / proof-contract naming refers to distinct concepts and is best resolved by a future glossary split, not this wave). One *new* footgun surfaced in the refactor step: `scripts/dojo-lint.sh` R4's regex matches ADR filenames of the form `NNNN-dojo-...` as if they were skill directories. Recorded in `HANDOFF.md → Improvement Backlog`. Workaround: reference ADRs by number only in skill prose.
- **Bigger picture status:** the proof-contract SoT is now properly anchored in the principle file. Wave 4's leading-word collapse for `_proof_` has its anchor file. Wave 2 (invocation rule) and Wave 10 (meta-skill as bridge) have their ADRs in place; they'll cite the existing decisions rather than re-derive them. Next dependency: Wave 2 can run immediately; it doesn't touch the lint script, the principle file, or the manual.
- **Promotion candidates:** the insight that *the proof contract is itself a kind of "enforce over instruct" — it converts "tests passed" prose into a sha256'd artifact an external observer can verify* — is general beyond this project. It's the kind of thing that belongs in `dojo-principles → Promoted (local)`. But: it's the *first* promotion candidate, and the `Promoted (local)` discipline says "earned by working sessions, not invented." I'd flag it for consideration at the end of the run (after several waves), not now.
- **Engagement note:** every gate this wave was approved without modification. Single wave, four stops (brief + failing test → GREEN diff + refactor assessment + decision → after refactor → commit gate), standard density. The gates worked: R10's failure mode was *exactly* what RED needed to surface; the refactor step caught a real lint regression (R4 false-positive on ADR filenames) that would otherwise have slipped into the commit. Supervised mode added value this wave.

## Wave 2 — Closing Debrief

- **What was done:** added `disable-model-invocation: true` to the YAML front-matter of the 7 user-invoked skills (randori, kaizen, kan, waza, tanren, kensha, kokai); added `# invocation: session-invoked — see ADR 0002` as a YAML comment to the 3 session-invoked skills (dojo-principles, dojo-project, dojo-conduct); added lint R11 to `scripts/dojo-lint.sh` enforcing the classification per the single `R11_CLASSIFY` table.
- **Why the approach works:** ADR 0002's three-bucket rule is now *enforceable* rather than aspirational. R11 catches three classes of mistakes: a skill added without a classification (R11 fails with "not classified"), a skill whose YAML doesn't match its bucket (e.g. user-invoked without the flag), and a future drift where someone flips a flag without updating the table. Trade-off accepted: session-invoked looks identical to model-invoked in the YAML parser; the rationale comment is what makes the distinction visible to humans and to grep. The refactor step consolidated the three category lists into a single `R11_CLASSIFY` table — the table is now the one place to look up or add a classification.
- **Systemic improvement opportunities:** two from the refactor assessment shipped (single-source-of-truth table; documented rationale-comment format). Three deferred per YAGNI: the redundant `Triggers on:` lines in user-invoked descriptions (Wave 3's router-table cleanup); a footer convention for skills (Wave 8); lint-script splitting (out of scope). One *new* footgun surfaced in the refactor step: the first attempt of the `R11_category` helper used a sed pattern with greedy `.*` that didn't produce output, breaking the gate; diagnosed and replaced with grep+cut. Recorded as a refactor-dojo checklist item.
- **Bigger picture status:** the invocation rule is now in force. ~480 words off the agent's always-on context (the 7 user-invoked skills' descriptions no longer load every turn). Wave 3 (router skill) can land with a category-aware table that points at the user-invoked skills — the cognitive-load cure the rule was designed to enable. Wave 4's leading-word collapse benefits from the smaller context. Any future skill addition must classify itself or fail the gate at PR time.
- **Promotion candidates:** the insight that *a rule about agent architecture (which skills the agent sees) is best enforced as a lint, not a guideline* — because the lint runs at every commit and the guideline relies on the next maintainer reading the ADR — is general. It's the inverse of the Wave 1 promotion candidate ("the proof contract IS a kind of enforce-over-instruct"). Together they suggest a `Promoted (local)` entry could read: "architecture rules become scripts; descriptions of architecture are seed material for scripts." But this is *still* a candidate; the discipline says "earned by working sessions, not invented." After Wave 10 ships and the package has used the pattern in three different rule types (proof contract, invocation, leading-word), the abstraction is earned.
- **Engagement note:** every gate this wave was approved without modification. Single wave, four stops (brief + failing test → GREEN diff + refactor assessment + decision → after refactor → commit gate), standard density. The gates worked again: R11 failed in RED with exactly the predicted 10 errors (7 missing flag + 3 missing comment); GREEN's 10 one-line edits made it pass; refactor consolidated three lists into one table without changing behavior (after one false start with sed backtracking, diagnosed and replaced). Two consecutive waves of "approved without modification" — *not yet* a pattern, but worth noting if Wave 3 lands the same way.
