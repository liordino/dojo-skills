A disciplined development system for AI agents

Dojo 道場

Turns an AI coding agent into a disciplined pair-programming partner — enforcing test-driven development in approval-gated waves, building a shared domain language, and keeping long sessions sharp through a compaction cycle.

Built for my own work and my own way of pairing with agents. Published only because someone might find it useful — or want to improve it together. Opinionated, deliberately specific in places, and not trying to be a universal framework. Fork freely, adapt mercilessly.

Philosophy

Three pillars

一

XP Pair Programming

You navigate — define what correct looks like, approve each step. The agent drives — writes code, runs checks, narrates its reasoning. Neither role is optional.

二

Test-Driven Development

Tests are the contract. A failing check written before implementation is the most precise expression of "what done means."

三

Goal-Driven Execution

Every wave is a verifiable outcome, not a task list. The agent derives the path; you define correct.

Rationale

Why waves instead of a rules file?

A flat AGENTS.md asks the agent to remember discipline. Dojo mechanizes it. The failure modes of a rules file map one-to-one onto Dojo mechanisms:


Silent scope creep → declared non-goals plus the kaizen gate.

"Tests passed" claims → the dojo-check proof artifact — only a real green run produces it.

Long-session context rot → the compaction cycle: everything durable on disk, each wave reloads lean.

Plans drifting from reality → divergence halts and re-grilling via /kaizen.

Rubber-stamp reviews → gates that ask for a decision with content, and an engagement note that calls it out when you stop deciding.

The kata cycle

One wave at a time

Each wave is a verifiable outcome. The agent stops for your decision at gates (supervised) or runs to completion (autonomous), halting only when reality diverges.

Entry
/hajime
Set rigor & mode, scaffold the project, grill the design, write the plan
›
Red
/kata-red
Write the failing check — the precise contract for this wave
›
Green
/kata-green
Minimum implementation to pass. YAGNI enforced
›
Commit
/kata-commit
Proof verified, artifacts updated, next wave loaded from .dojo/TASKS.md

↺  Repeats per wave until .dojo/TASKS.md is complete, or the wave ceiling triggers a clean pause with .dojo/session/resume.md

The mode — chosen every session, at /hajime

Supervised The agent stops at gates for your decision; you set the gate density — full, standard, or light. Engagement notes keep rubber-stamping visible
Autonomous The agent runs the cycle to completion, commits included — halting only when reality diverges, pausing at the wave ceiling with a clean checkpoint and .dojo/session/resume.md

12 skills

The skill set

Each skill is a SKILL.md file — terse normative rules the agent loads. Rationale and walkthroughs live in the manual, which the agent never loads.

Always loaded — every session
dojo-principles
Cross-cutting engineering rules for the code itself — navigation, DRY, minimal delta, negative space, purity, logging, ECS, and your promoted insights
dojo-project
Project-level rules — structure, docs, config, entrypoints, the global preferences store, and the preferences-vs-insights promotion rule
dojo-conduct
How the agent behaves — the precedence hierarchy, evidence gates, gate density, concise output, and optional tool treatment
Session entry
hajime
Session start (feature or bugfix) — asks rigor (real/PoC) and mode, scaffolds the project, runs the design grill; bugfix branch routes to kan diagnosis
The kata steps
kata-red
Write the failing check — invariant-based, property-first strategy ladder; the algorithm-approach discipline lives here
kata-green
Minimum implementation — YAGNI, idempotency, explicit types, error propagation; includes the refactor step and the two-attempt stuck branch inline
kata-commit
Commit the wave — proof-verified gate, explicit staging with denylist, debrief, .dojo/TASKS.md advancement, wave ceiling
Techniques — called from the cycle
randori
Interview-driven design grill — domain language, ADRs, the .dojo/TASKS.md plan. Scoping mode when answers live elsewhere
kan
Disciplined diagnosis — reproduce → minimise → hypothesise → instrument → fix → regression-test
tanren
Iterative optimization — forge a better algorithm by propose → score → keep-or-revert, gated on a measurable metric and a frozen scorer
kaizen
Re-grill and rewrite the plan on pivots or divergence halts. Never writes code
kokai
Release and distribution — problem-first README, CI mirrors dojo-check, build-once packaging, the bin/deploy contract

Engineering principles

What the agent internalizes

Rules, not guidelines — split across three governing skills by scope.

Code navigation rg for text frequency, ast-grep for structure. Never the wrong tool for the question
Minimal delta Survey first. Build the smallest delta that fully achieves the outcome
Negative space Make invalid states unrepresentable — in types, before runtime checks
Parse, don't validate parse(input) → Narrow. The output type is narrower than the input — that is the point
Function purity Functional core, imperative shell. IO lives at the boundary; logic stays pure
Errors as values Expected failures return Result/error. Exceptions are for the truly exceptional
Deterministic first Probabilistic only when deterministic is genuinely impossible — and never silently chosen
Structured logging JSON Lines at the boundary. Injected LogSink interface. Never secrets, never prose
Enforce over instruct If a rule can be a script, make it a script. Gates verify evidence, not claims
Precedence hierarchy Human instruction → governance files → project files → skill text → memory
Gate density full / standard / light — same content, fewer stops. Never skip, only batch
Promoted insights Per-project learnings earn global status only by deliberate, consented promotion
One wave, every repo A wave spanning repositories closes in every one it touched — each record carries the commit, proof, and counterpart hash
Mirror metadata Never the source of truth: derive indices from the authoritative collection; mirror writes must be loud — silent no-op inserts desync permanently

Living artifacts

Everything durable on disk

The compaction cycle works because every durable fact has a home. The agent forgets wave context — the files don't.

  • .dojo/TASKS.md
    The plan — every wave a verifiable outcome with a status. Written by randori, advanced by kata-commit, rewritten by kaizen
  • .dojo/TASKS.md · Improvement Backlog
    Revisit items — not a plan, not a commitment. Promoted into a wave via kaizen when the moment is right. There is no snapshot document: a cold reader orients from .dojo/CONTEXT.md, .dojo/TASKS.md, .dojo/progress.md, and git log
  • .dojo/session/dojo-session.md
    Current wave state — mode, rigor, step, goal, attempts. Gitignored; per-machine
  • .dojo/CONTEXT.md · .dojo/adr/
    Glossary · Non-Goals · Decisions. Three sections, nothing else. The domain contract. Decision records with rationale accumulate under .dojo/adr/ as they are made
  • .dojo/learning-log.md
    Per-wave debriefs (briefs in supervised sessions). Append-only
  • .dojo/progress.md
    The single terse per-wave log — built, exposes, next dependency, commit hash
  • .dojo/findings.md
    Discoveries and halt diagnostics. Append-only
  • .dojo/proof/check-proof
    Evidence the gate actually ran — timestamp, exit 0, output hash. Verified by kata-commit before every commit
  • .dojo/session/resume.md
    One-line continuation pointer written at the autonomous wave ceiling

Get started

Install

# everything $ npx skills add liordino/dojo-skills # be selective $ npx skills add liordino/dojo-skills --skill hajime --skill kata-red

Or copy the skill directories manually — each is a folder containing a SKILL.md. Then run /hajime on a new project; it scaffolds everything else.

Two checks before editing Dojo's own skills

Both tools live in this repo — an install carries only the skill directories, so they gate Dojo's own development, not your project.

# internal consistency (enums, headings, canonical template) $ ./scripts/dojo-lint.sh # proof contract, end-to-end on a fixture repo $ ./evals/run-mechanics.sh

The names

道場 — the training hall

A dojo is the place where discipline is built. A kata is a form practiced until internalized — not a ruleset you consult, but a form you execute automatically. That is the intent.
